# Гоночные условия — Race Condition

## Что это такое

Race Condition возникает, когда результат операции зависит от порядка выполнения параллельных запросов или процессов. В веб-приложениях это особенно опасно для действий, которые сначала проверяют состояние, а затем его изменяют.

Классический пример — покупка товара:

1. Сервер проверяет, что на складе есть один товар.
2. Сервер создаёт заказ.
3. Сервер уменьшает остаток.

Если два запроса проходят проверку одновременно, оба могут увидеть один и тот же остаток и создать два заказа.

## Уязвимый сценарий

Логика вроде этой небезопасна:

```python
if product.stock > 0:
    create_order(user, product)
    product.stock -= 1
    save(product)
```

Между проверкой `stock > 0` и сохранением есть окно, в которое может попасть другой запрос.

Другие распространённые цели:

- повторное использование купона или бонуса;
- вывод денег и изменение баланса;
- регистрация уникального имени;
- смена email или пароля;
- выдача приглашения или одноразового токена;
- создание нескольких платежей по одной операции.

## Как проверять в лаборатории

Проверку нужно проводить только на своей системе или на разрешённой CTF-машине.

1. Найти запрос, который меняет состояние.
2. Зафиксировать состояние до отправки: остаток товара, баланс, статус купона.
3. Повторить один и тот же запрос параллельно, а не последовательно.
4. Сравнить число созданных объектов и итоговое состояние.
5. Проверить, не произошёл ли побочный эффект: отрицательный остаток, двойное списание или повторная выдача бонуса.

Для ручной проверки удобно подготовить несколько одинаковых запросов в Burp Repeater и отправить их одновременно. В автоматизированной лаборатории можно использовать небольшой скрипт с ограниченным числом параллельных запросов. Большой поток запросов для этой проверки не нужен.

## TOCTOU

Один из вариантов race condition называется TOCTOU — Time Of Check to Time Of Use. Проблема возникает, когда объект проверяется в один момент, а используется позже, уже после того как его состояние могло измениться.

Пример:

```text
проверить: купон ещё не использован
изменить: отметить купон использованным
```

Обе операции должны быть частью одной атомарной транзакции. Иначе несколько параллельных запросов могут пройти проверку до того, как первый успеет изменить состояние.

## Как исправлять

### Атомарное изменение в базе

Вместо раздельной проверки и обновления условие нужно включить в сам SQL-запрос:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = :product_id
  AND stock > 0;
```

После выполнения сервер проверяет количество изменённых строк. Если оно равно `1`, резервирование прошло; если `0`, товара уже нет.

### Транзакции и блокировки

Для связанных операций нужно использовать транзакцию с подходящим уровнем изоляции и блокировкой строки. Блокировка должна быть короткой и охватывать проверку вместе с изменением.

### Уникальные ограничения

База данных должна дополнительно защищать бизнес-правило:

```sql
UNIQUE(user_id, coupon_id)
```

Такой constraint не позволит одному пользователю зарегистрировать один купон дважды даже при ошибке в коде приложения.

### Идемпотентность

Для платежей и заказов полезен уникальный `Idempotency-Key`. Повтор одинакового запроса с тем же ключом должен вернуть результат первой операции, а не создать новую.

## Что фиксировать в отчёте

- исходное состояние объекта;
- точку входа и HTTP-запрос;
- число параллельных запросов;
- результат каждого запроса;
- итоговое состояние в базе;
- влияние на конфиденциальность, целостность или доступность данных;
- способ исправления и повторную проверку после исправления.

## Вывод

Race Condition — это не просто «слишком быстрые запросы». Это ошибка в согласованности бизнес-операции. Надёжная защита должна находиться на сервере и в базе данных: атомарное обновление, транзакции, уникальные ограничения и идемпотентность должны исключать зависимость результата от случайного порядка запросов.
