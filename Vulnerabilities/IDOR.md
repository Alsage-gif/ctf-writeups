# IDOR — Insecure Direct Object Reference

## Что это такое

IDOR возникает, когда приложение принимает идентификатор объекта от клиента, но не проверяет, имеет ли текущий пользователь право работать именно с этим объектом.

Пример: пользователь открывает свой заказ `/api/orders/9987`, меняет номер на `/api/orders/9988` и получает чужие данные. Сам факт существования ID не должен давать доступ к объекту.

## Как выглядит проверка

Типичные точки для ручного тестирования:

```http
GET /api/users/profile?id=500
GET /api/orders/view/9987
GET /api/chat/get_messages?chat_id=15
```

Я меняю идентификатор и сравниваю ответы для объектов текущего пользователя и другого пользователя. Важно проверять не только HTTP-код, но и содержимое ответа, побочные эффекты и возможность изменения данных.

## Причина уязвимости

Небезопасный запрос проверяет только существование объекта:

```sql
SELECT * FROM orders WHERE order_id = $USER_INPUT;
```

Проверка должна учитывать владельца или другой серверный контекст авторизации:

```sql
SELECT *
FROM orders
WHERE order_id = $USER_INPUT
  AND owner_id = $CURRENT_SESSION_USER_ID;
```

Если объект принадлежит другому пользователю, сервер должен вернуть `403 Forbidden` или нейтральный `404 Not Found`, не раскрывая существование записи.

## Что проверять на пентесте

- GET, POST, PUT, PATCH и DELETE для одного и того же объекта;
- числовые ID, UUID и идентификаторы в JSON-телах;
- подмену параметров, включая повторяющиеся параметры;
- ссылки на объекты в профилях, чатах, уведомлениях и публичных комментариях;
- различия в поведении при обращении от имени двух тестовых пользователей.

UUID усложняет перебор, но не исправляет отсутствие авторизации: если UUID попал в ответ или ссылку, его всё равно нужно проверять на принадлежность текущему пользователю.

## Инструменты

- Burp Repeater — ручная подмена ID и сравнение ответов;
- Burp Intruder — проверка небольшого диапазона идентификаторов в разрешённой лаборатории;
- Autorize — автоматическое сравнение запросов с разными сессиями.

## Исправление

Авторизацию нужно проверять на сервере для каждой операции и каждого объекта. Нельзя полагаться на скрытые поля, Base64, UUID или ограничения интерфейса. Дополнительно полезны единый слой проверки доступа, безопасные ответы `403/404`, журналирование отказов и тесты на горизонтальное и вертикальное повышение привилегий.
