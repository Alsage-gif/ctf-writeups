## Что делает XSS

Причин для этого много Уязвимости всё ещё встречаются в веб-приложениях. Ниже мы перечислим некоторые из них.

**Недостаточная проверка и санитарная обработка вводных данных**

Веб-приложения принимают пользовательские данные, например, через формы, и используют эти данные для динамической генерации HTML-страниц. Следовательно, вредоносные скрипты могут быть встроены в легитимный вход и в конечном итоге будут выполнены браузером, если не быть должным образом очищены.

**Отсутствие выходного кодирования**

Пользователь может использовать различные символы для изменения того, как веб-браузер обрабатывает и отображает веб-страницу. **Неправильное использование заголовков безопасности**

Различные заголовки безопасности помогают устранять уязвимости XSS. Например, Content Security Policy (CSP) снижает риски XSS, определяя, какие источники доверяют для исполняемых скриптов. Неправильно настроенный CSP, например, чрезмерно разрешительные политики или неправильное использование `unsafe-inline` или `unsafe-eval` директив может облегчить атакующему выполнение своих Полезные нагрузки.

**Уязвимости фреймворка и языка**

Некоторые старые веб-фреймворки не предоставляли механизмов безопасности против ; другие были сняты с патча уязвимости. Современные веб-фреймворки автоматически избегают По замыслу и быстро устранять обнаруженную уязвимость.

**Сторонние библиотеки**

Интеграция сторонних библиотек в веб-приложении может привести к появлению уязвимости; Даже если основное веб-приложение не уязвимо.

### PHP

**Уязвимый код**

Посмотрите следующий фрагмент кода в PHP и выясните, почему он может быть уязвим к отражению .

```php
<?php
$search_query = $_GET['q'];
echo "<p>You searched for: $search_query</p>";
?>
```

Если вы не знакомы с , `$_GET` — это массив PHP, содержащий значения из строки запроса URL. Кроме того,, `$_GET['q']` ссылается на параметр строки запроса `q`. Например, в `http://shop.thm/search.php?q=table`, `$_GET['q']` имеет ценность `table`.

Как вы, возможно, догадались, уязвимость вызвана значением поиска, отображаемым на странице результатов без очистки. Таким образом, злоумышленник может добавить вредоносный скрипт к URL, зная, что он будет выполнен. Например, в качестве доказательства концепции можно проверить следующий URL: `http://shop.thm/search.php?q=<script>alert(document.cookie)</script>` Если сайт уязвим, появится окно оповещения с куки-файлами пользователя.

**Фиксированный код**

К счастью, исправить этот код просто.

```php
<?php
$search_query = $_GET['q'];
$escaped_search_query = htmlspecialchars($search_query);
echo "<p>You searched for: $escaped_search_query</p>";
?>
```

The Функция `htmlspecialchars()` преобразует специальные символы в HTML-сущности. Персонажи `<`, `>`, `&`, `"`, `'` заменяются по умолчанию, чтобы предотвратить выполнение скриптов на входе. Вы можете прочитать его документацию [Вот. (Открывается в новой вкладке)](https://www.php.net/htmlspecialchars).

Если вы не знакомы с Node.js, приведённый выше фрагмент кода использует Express — популярный фреймворк веб-приложений для Node.js. The `req.query.q` извлечет значение `q`. Например, в `http://shop.thm/search?q=table`, `req.query.q` имеет ценность `table`. Наконец, ответ генерируется путем добавления поискового запроса, предоставленного пользователем, в раздел «Вы искали:”.

```javascript
const express = require('express');
const sanitizeHtml = require('sanitize-html');

const app = express();

app.get('/search', function(req, res) {
    const searchTerm = req.query.q;
    const sanitizedSearchTerm = sanitizeHtml(searchTerm);

});

app.listen(80);
```

Решение достигается с помощью `sanitizeHtml()` Из `sanitize-html` Библиотека. Эта функция удаляет опасные элементы и атрибуты. Это включает удаление скрипт-тегов и других элементов, которые могут использоваться в вредоносных целях. Вы можете прочитать его документацию [Вот. **Фиксированный код**

```python
from flask import Flask, request
from html import escape

app = Flask(__name__)

@app.route("/search")
def home():
    query = request.args.get("q")
    escaped_query = escape(query)
    return f"You searched for: {escaped_query}!"

if __name__ == "__main__":
    app.run(debug=True)
```

Главное изменение в том, что пользовательский ввод теперь срабатывает с помощью `escape()` функция из `html` модуля. Обратите внимание, что `html.escape()` функция в Flask на самом деле является псевдонимом для `markupsafe.escape()`. Оба они из библиотеки Werkzeug и служат одной и той же цели: убегать от опасных персонажей в нитях. Эта функция преобразует такие символы, как `<`, `>`, `"`, `'` в HTML-сущности, обезвреживая любой вредоносный код, вставленный пользователем.

Разбор кода эксплойта

1. **URL-кодированная часть**:  
    `?k304=y%0D%0A%0D%0A%3Cimg+src%3Dcopyparty+onerror%3Dalert(1)%3E`
    - `%0D%0A`: Это символы переноса строки (CRLF). Они используются для того, чтобы «обмануть» сервер и заставить его вставить вредоносный код в тело страницы, обойдя некоторые фильтры.
    - `%3C` и `%3E`: Символы `<` и `>`.
2. **Декодированный результат**:  
    `?k304=y <img src=copyparty onerror=alert(1)>`
    - **`<img ...>`**: Тег изображения.
    - **`src=copyparty`**: Атрибут указывает на несуществующий файл изображения.
    - **`onerror=alert(1)`**: Это обработчик события. Поскольку файла «copyparty» не существует, возникает ошибка, которая автоматически выполняет JavaScript-код `alert(1)`. В реальной атаке вместо безобидного окна `alert` может быть код для кражи сессий (куки) или выполнения действий от имени пользователя.

Суть проблемы

Сервер **copyparty** некорректно обрабатывал параметр `k304` и возвращал его пользователю в составе HTML-страницы без надлежащей очистки (экранирования). Это позволяло злоумышленнику отправить жертве специально сформированную ссылку, при нажатии на которую в браузере жертвы выполнялся сторонний код.

Причина некорректной обработки параметра `k304` в программе **copyparty** сводится к классической ошибке веб-разработки: **отсутствию фильтрации и экранирования входных данных**.

Вот детали того, что именно шло не так (согласно разбору уязвимости **CVE-2023-38501**):

1. Роль параметра `k304`

В архитектуре `copyparty` этот параметр использовался для внутренних нужд — в частности, для генерации и установки **куки-файлов (cookies)**. Когда вы переходите по ссылке с этим параметром, сервер берет его значение и пытается «запомнить» его для вашей сессии.

## stored xss , или Persistent xss , — 
это уязвимость безопасности веб-приложения, возникающая при сохранении вводных данных, предоставленных пользователем, а затем встраивает их в веб-страницы, предоставляемые другим пользователям без надлежащей очистки или выхода. Примеры включают посты на веб-форумах, обзоры продуктов, комментарии пользователей и другие хранилища данных. Другими словами, хранится происходит, когда ввод пользователя сохраняется в хранилище данных и затем включен в веб-страницы, предоставляемые другим пользователям без достаточного выхода.

## Stored xss
Начинается с того, что злоумышленник вводит вредоносный скрипт в поле ввода уязвимого веб-приложения. Уязвимость может заключаться в том, как веб-приложение обрабатывает данные в комментариях, постах на форуме или разделе информации о профиле. Когда другие пользователи получают доступ к этому хранимому контенту, введённый вредоносный скрипт запускается внутри их браузеров. Скрипт может выполнять широкий спектр действий — от кражи сессионных файлов cookie до выполнения действий от имени пользователя без его согласия.

## Уязвимое веб-приложение

Существует множество причин, по которым веб-приложение может быть уязвимо к сохранению . Некоторые из лучших практик по предотвращению хранения Уязвимости таковы::

- **Проверяйте и дезинфицируйте данные**: Определите чёткие правила и обеспечьте строгую проверку всех данных, предоставленных пользователем. Например, в имени пользователя могут использоваться только буквенно-цифровые символы, а в возрастных полях разрешены только целые числа.
- **Используйте выходной выход**: При отображении пользовательских данных в контексте HTML кодировать все специфические для HTML символы, такие как `<`, `>`, и `&`.
- **Применить контекстно-специфическое кодирование**: Например, в контексте JavaScript мы должны использовать JavaScript-кодирование всякий раз, когда вставляем данные в JavaScript-код. С другой стороны, данные, размещаемые в URL, должны использовать соответствующие методы кодирования URL, такие как процентное кодирование. Цель — обеспечить действительность URL при предотвращении внедрения скриптов.
- **Глубокая практика защиты**: Не полагайтесь только на один уровень защиты; Используйте серверную валидацию, а не полагаясь исключительно на клиентскую валидацию.

В следующих примерах мы перечисляем уязвимые фрагменты кода на различных языках. На этот раз это задание должно быть простым, так как решения похожи на ранее реализованные решения.

```php
    $sanitizedComment = htmlspecialchars($row['comment']);
```

Перед тем как показать каждый комментарий на экране, мы пропускаем его через `htmlspecialchars()` функции для преобразования всех специальных символов в HTML-сущности. Следовательно, любые попытки сохранить XSS не попадут в браузер конечного пользователя.

Нас интересует устранение хранящихся уязвимостей XSS. Нужно убедиться, что в базе данных не сохраняются вредоносные скрипты; кроме того, мы будем избегать любого контента до его отображения в виде HTML.

```python
from flask import Flask, request, render_template_string, escape
from flask_sqlalchemy import SQLAlchemy
from markupsafe import escape

app = Flask(__name__)
app.config['SQLALCHEMY_DATABASE_URI'] = 'sqlite:///site.db'
db = SQLAlchemy(app)

class Comment(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    content = db.Column(db.String, nullable=False)

@app.route('/comment', methods=['POST'])
def add_comment():
    comment_content = request.form['comment']
    comment = Comment(content=comment_content)
    db.session.add(comment)
    db.session.commit()
    return 'Comment added!'

@app.route('/comments')
def show_comments():
    comments = Comment.query.all()
    sanitized_comments = [escape(c.content) for c in comments]
    return render_template_string(''.join(['<div>' + comment + '</div>' for comment in sanitized_comments]))
```

Хотя ввод, приведённый пользователем `request.form['comment']` сохраняется дословно, содержимое каждого сохранённого комментария `c` проходит через функцию escape() перед отправкой в браузер пользователя для отображения в виде HTML.

## Уязвимые веб-приложения

Уязвимости XSS на базе DOM возникают внутри браузера. Им не нужно заходить на сервер и возвращаться в браузер клиента. Другими словами, злоумышленник попытается воспользоваться этой ситуацией, внедрив вредоносный скрипт, например, в URL, и он будет выполняться на стороне клиента без участия сервера. Мы представим элементарный и минимально статический сайт без использования бэкенд-кода для демонстрации этой концепции.

### Уязвимый «статичный» сайт

```html
<!DOCTYPE html>
<html>
<head>
    <title>Vulnerable Page</title>
```

3. Наконец, структура DOM справа остаётся нетронутой; The `<body>` у него трое непосредственных детей.

### Исправленный «статичный» сайт

```html
<!DOCTYPE html>
<html>
<head>
    <title>Secure Page</title>
</head>
<body>
    <div id="greeting"></div>
    <script>
        const name = new URLSearchParams(window.location.search).get('name');
        // Escape the user input to prevent XSS attacks
        const escapedName = encodeURIComponent(name);
        document.getElementById("greeting").textContent = "Hello, " + escapedName;
    </script>
</body>
</html>
```

Один из способов исправить эту страницу — избегать добавления пользовательского ввода напрямую с помощью `document.write()`. Вместо этого мы сначала избежали пользовательского ввода с помощью `encodeURIComponent()` а затем добавил его в `textContent`.

Предыдущая попытка сейчас не работает. Мы видим это:

1. Пользователь добавил JavaScript в свой вклад.
2. JavaScript-код отображается в виде закодированных символов и не представляет угрозы в текущем контексте.
3. Структура DOM больше не затрагивается, когда пользователь пытается добавить код в своё имя.

## Контекст

Введённая полезная нагрузка, скорее всего, попадёт в одну из следующих:

- Между HTML-тегами
- Внутри HTML-тегов
- Внутри JavaScript

Когда происходит между HTML-тегами, злоумышленник может запустить `<script>alert(document.cookie)</script>`.

Однако, когда инъекция находится внутри HTML-тега, нужно завершить HTML-тег, чтобы скрипт загрузился. В результате мы можем адаптировать нашу полезную нагрузку к `><script>alert(document.cookie)</script>` или `"><script>alert(document.cookie)</script>` Или что-то похожее, что подойдёт в контекст.

Возможно, нам придётся завершить скрипт для запуска вставленного, если мы сможем внедрить XSS в существующий JavaScript. Например, можно начать с `</script>` чтобы закончить сценарий и продолжить дальше. Если ваш код находится внутри JavaScript-строки, вы можете закрыть строку с помощью `'`, Выполните команду с точкой с запятой, выполните команду и прокомментируйте остальную строку `//`. Можно попробовать что-то вроде этого `';alert(document.cookie)//`.

Этот пример даст вам идеи, как выйти из исходного контекста. В целом, знание контекста, в котором выполняется ваша XXS-нагрузка, очень важно для успешного выполнения нагрузки.

## Уклонение

Для создания вашей пользовательской XSS-нагрузки можно обратиться к различным репозиториям. Это даёт вам достаточно пространства для экспериментов. Один из таких списков — [Список полезной нагрузки XSS (Открывается в новой вкладке)](https://github.com/payloadbox/xss-payload-list).

Однако иногда существуют фильтры, блокирующие XSS-нагрузки. Если существует ограничение, основанное на длине полезной нагрузки, то [Крошечные полезные нагрузки XSS (Открывается в новой вкладке)](https://github.com/terjanq/Tiny-XSS-Payloads) Это может быть отличной отправной точкой, чтобы обойти ограничения по длине.

Если XSS-полезные нагрузки блокируются на основе определённых блок-листов, существуют различные приёмы уклонения. Например, горизонтальная вкладка, новая линия или возврат каретки могут разрушить полезную нагрузку и избежать обнаружения двигателей.

- Горизонтальная вкладка (TAB) — это `9` В шестнадцатеричном представлении
- Новая линия (LF) — `A` В шестнадцатеричном представлении
- Возврат каретки (CR) равен `D` В шестнадцатеричном представлении

Следовательно, основываясь на [Шпаргалка по уклонению фильтра XSS (Открывается в новой вкладке)](https://cheatsheetseries.owasp.org/cheatsheets/XSS_Filter_Evasion_Cheat_Sheet.html), Мы можем разбить полезную нагрузку. `<IMG SRC="javascript:alert('XSS');">` по-разному:

```javascript
<IMG SRC="jav&#x09;ascript:alert('XSS');">
<IMG SRC="jav&#x0A;ascript:alert('XSS');">
<IMG SRC="jav&#x0D;ascript:alert('XSS');">
```

Существует сотни техник уклонения; Выбор зависит от безопасности цели и требует проб и ошибок для достижения успешного результата.
