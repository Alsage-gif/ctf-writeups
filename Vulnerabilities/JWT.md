# JWT — проверка безопасности токенов

## Что такое JWT

JWT (JSON Web Token) — формат передачи утверждений между клиентом и сервером. Обычно токен состоит из трёх частей:

```text
header.payload.signature
```

Первые две части кодируются в Base64URL и не являются шифрованием. Поэтому содержимое JWT можно прочитать без знания секрета. Секретная часть — подпись, с помощью которой сервер должен проверить, что токен не изменяли.

Пример структуры:

```json
// Header
{
  "alg": "HS256",
  "typ": "JWT"
}
```

```json
// Payload
{
  "sub": "user-123",
  "role": "user",
  "iss": "https://auth.example.test",
  "aud": "web-app",
  "iat": 1710000000,
  "exp": 1710003600
}
```

В payload нельзя хранить пароли, API-ключи или другую чувствительную информацию: Base64URL легко декодируется.

## Что проверять при тестировании

1. Получить тестовый JWT из cookie или заголовка `Authorization`.
2. Декодировать header и payload локально, не отправляя реальный токен на сторонние сайты.
3. Изменить один claim, например `role`, `sub` или `exp`.
4. Отправить запрос с изменённым токеном.
5. Убедиться, что сервер отклоняет его с `401` или `403`.

Пример запроса:

```http
GET /api/profile HTTP/1.1
Host: app.example.test
Authorization: Bearer <JWT>
```

Проверять нужно не только ответ профиля, но и операции, которые требуют другой роли: просмотр чужих объектов, изменение настроек и административные функции.

## Типичные ошибки

### 1. Доверие к изменённым claims

Если сервер принимает изменённый `role=admin` или чужой `sub`, это ошибка авторизации. Claims из токена можно использовать только после успешной проверки подписи и доверия к issuer.

### 2. Неправильная обработка алгоритма

Сервер не должен принимать произвольное значение `alg` из токена. Алгоритм должен быть заранее задан конфигурацией конкретного issuer. Исторический вариант атаки — подмена алгоритма на `none`; современные библиотеки обязаны отклонять такие токены.

### 3. Смешение RS256 и HS256

При асимметричной схеме RS256 подпись создаётся приватным ключом и проверяется публичным. Нельзя позволять клиенту выбирать алгоритм или использовать публичный ключ как HMAC-секрет для HS256. Сервер должен жёстко связывать issuer, алгоритм и ключ.

### 4. Слабый HMAC-секрет

Для HS256 нужен длинный случайный секрет. Предсказуемый секрет может позволить офлайн-подбор подписи. В учебной лаборатории это можно проверять специализированными инструментами, но не следует делать это для чужих токенов.

### 5. Отсутствие проверки стандартных claims

Сервер должен проверять как минимум:

- `exp` — срок действия;
- `nbf` — момент, раньше которого токен недействителен;
- `iss` — доверенный issuer;
- `aud` — предназначение токена;
- `sub` — идентификатор субъекта, если он используется в авторизации.

### 6. Непродуманное завершение сессии

JWT часто живёт дольше, чем нужно. Для снижения риска используют короткоживущие access-токены, refresh-токены с ротацией, отзыв скомпрометированных сессий и повторную аутентификацию для критичных действий.

## Признаки защищённой реализации

- разрешённый алгоритм задан на сервере, а не взят из пользовательского header;
- подпись проверяется до чтения claims для авторизации;
- `iss`, `aud`, `exp` и `nbf` валидируются;
- права пользователя дополнительно проверяются на сервере для каждого объекта;
- секреты хранятся вне репозитория и регулярно ротируются;
- JWT не содержит чувствительные данные и не используется как замена серверной проверке доступа.

## Вывод

JWT — это подписанный контейнер с данными, а не зашифрованный пароль. Сам факт, что payload удалось декодировать, не является уязвимостью. Уязвимость появляется тогда, когда сервер принимает изменённые claims, не проверяет подпись или неправильно обрабатывает срок действия и назначение токена.
