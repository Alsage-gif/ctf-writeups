## Анализ скрипта feedback.sh

После получения доступа я разобрал `/opt/NewComponent/feedback.sh`. Критичная строка выглядела так:

```bash
eval "echo $feedback"
```

`eval` повторно разбирает содержимое переменной как команду shell. Поэтому спецсимволы из отзыва могли влиять не только на вывод, но и на структуру выполняемой команды.

Разработчик использовал blacklist: запрещал обратные кавычки, `$(`, `|`, `&`, `;`, `!`, `?`, `*`, `\` и закрывающую скобку. При этом символ перенаправления `>` остался разрешённым.

Дополнительная проблема заключалась в том, что сам скрипт запускался через `sudo`. Значит, операция перенаправления выполнялась с правами root.

## Повышение привилегий

Я использовал разрешённый оператор `>` для записи правила в `/etc/sudoers.d/deku`:

```text
deku ALL=NOPASSWD:ALL
```

После этого пользователь `deku` получил возможность выполнять команды через `sudo` без пароля. Финальная проверка была простой:

```bash
sudo cat /root/root.txt
```

## Вывод

Цепочка атаки состояла из двух ошибок:

1. пользовательский ввод передавался в `eval`;
2. уязвимый скрипт разрешалось запускать через `sudo`.

Blacklist не должен использоваться как основная защита командного интерпретатора. Надёжнее убрать `eval`, передавать аргументы в безопасной форме и разрешать только ожидаемый формат данных.

Также необходимо удалить широкое правило `NOPASSWD:ALL`, ограничить `sudo` конкретными командами и проверить права на `/opt/NewComponent/feedback.sh`.
