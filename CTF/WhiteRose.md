## EJS и получение RCE

После дальнейшего анализа я решил проверить, как приложение обрабатывает ошибки. Обычный запрос возвращал код `200`, но удаление параметра `password` вызывало ошибку сервера.

![Запрос, который возвращает корректный ответ](../images/Pasted%20image%2020260825005922.png)

![Запрос без параметра password](../images/Pasted%20image%2020260825010005.png)

![Информация, раскрытая сообщением об ошибке](../images/Pasted%20image%2020260825010040.png)

В стектрейсе упоминался EJS — шаблонизатор Embedded JavaScript.

![Упоминание EJS в сообщении об ошибке](../images/Pasted%20image%2020260825010336.png)

По расположению функций в исходном коде я предположил, что используется ветка EJS 3.1.x. Это помогло подобрать совместимый вариант проверки, но версия библиотеки сама по себе ещё не доказывала наличие RCE.

![Определение версии EJS по структуре исходного кода](../images/Pasted%20image%2020260825011804.png)

Сначала проверил CVE-2022-29078, но первая нагрузка не дала стабильного подтверждения. После этого изучил [issue #735 в репозитории EJS](https://github.com/mde/ejs/issues/735) и адаптировал нагрузку под конкретное приложение.

![Первая проверка EJS и результат обработки payload](../images/Pasted%20image%2020260825014746.png)

С корректной нагрузкой удалось получить выполнение команд на сервере.

![Подтверждение RCE через EJS](../images/Pasted%20image%2020260825020529.png)

После получения соединения стабилизировал shell:

```bash
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl+Z
stty raw -echo; fg
export TERM=xterm
```

![Стабилизация reverse shell](../images/Pasted%20image%2020260825020751.png)

## Повышение привилегий через `sudoedit`

При проверке разрешённых команд выяснилось, что пользователь мог запускать `sudoedit` для конфигурации Nginx. Версия sudo была `1.9.12p1`.

Ключевой особенностью `sudoedit` стало то, что он позволяет пользователю редактировать разрешённый файл через выбранный редактор. Уязвимость CVE-2023-22809 позволяет манипулировать переменной `EDITOR` и передавать редактору дополнительный файл.

Команда из решения:

```bash
EDITOR="nano -- /etc/crontab" sudoedit /etc/nginx/sites-available/admin.cyprusbank.thm
```

В результате через разрешённый механизм редактирования удалось получить доступ к `/etc/crontab` и использовать cron для выполнения команды с повышенными привилегиями.

![Эксплуатация sudoedit и редактирование системного файла](../images/Pasted%20image%2020260825022108.png)

![Результат повышения привилегий](../images/Pasted%20image%2020260825022257.png)

Второй флаг:

```text
THM{4nd_uR_p4ck4g3s}
```

## Итоговая цепочка

```text
Сканирование
  → поиск субдомена
  → IDOR в message
  → учётные данные администратора
  → раскрытие EJS через ошибку
  → EJS RCE
  → reverse shell
  → sudoedit / CVE-2023-22809
  → root и второй флаг
```

## Выводы

- Всегда проверять субдомены, если основное приложение не даёт точек входа.
- IDOR нужно искать не только в URL, но и во вкладках, сообщениях и API-запросах.
- Стектрейсы могут раскрыть используемые библиотеки и версии, но версию нужно подтверждать несколькими признаками.
- Payload необходимо сопоставлять с конкретной версией библиотеки и логикой приложения, а не копировать без проверки.
- В `sudo` важно различать право запускать программу и право безопасно редактировать файл через эту программу.
- После получения shell нужно проверять версии утилит, права на конфигурации, cron и доступные переменные окружения.
